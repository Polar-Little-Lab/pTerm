# 공통 릴리스 기준

pGit과 pTerm은 이 절차를 함께 사용합니다. 기술 스택과 지원 플랫폼의 차이는 유지합니다.

1. 작업 브랜치에서 수정하고 PR을 만듭니다. 기존 기능·UI를 의도 없이 제거하거나 재설계하지 않습니다. 의도적인 변경은 이유와 사용자 영향을 기록합니다.
2. 마지막 정식 태그부터의 변경을 검토합니다. 버그 수정은 patch, 호환되는 기능 추가는 minor, 호환성이 깨지는 변경은 major 버전으로 계획합니다. 문서·CI 수정만으로 앱 버전을 올리지는 않습니다.
3. 모든 버전 원본과 잠금 파일을 맞추고 `node scripts/check-release.mjs`를 실행합니다. 릴리스 노트는 `docs/release-template.md`의 항목을 빠짐없이 작성합니다. 과거 노트를 현재 기능처럼 다시 쓰지 않습니다.
4. 프로젝트별 기존 테스트와 변경된 사용자 흐름을 검사합니다. `docs/product-baseline.md`의 동작 보존 기준을 확인합니다. 스냅샷을 무조건 갱신하거나 timeout을 늘려 실패를 숨기지 않습니다.
5. PR 검사가 성공하면 main에 병합합니다. main 검사도 성공한 것을 확인한 뒤 해당 커밋에 `v<version>` 태그를 만듭니다. 릴리스는 태그로 실행하며 수동 실행의 기본값은 검증 빌드입니다.
6. GitHub Actions에서 macOS Developer ID 서명, Apple 공증, stapler 및 Gatekeeper 검증을 수행합니다. 플랫폼·아키텍처별 파일, 내부 버전, 설치/실행, SHA256SUMS를 확인한 다음 게시합니다. 비밀 값은 로그나 저장소에 넣지 않습니다.
7. 게시한 태그·설치 파일은 덮어쓰지 않습니다. 수정 배포는 새 버전으로 진행합니다. 이미 검증한 파일을 승격할 때는 소스 트리와 해시 일치를 증명합니다.
8. 결과에는 PR, main SHA, 태그, Actions URL, 실제 통과한 검사와 미확인 사항을 남깁니다. PR 성공만으로 main 성공이나 앱 배포 완료를 주장하지 않습니다.

## 스킬

로컬 공통 스킬: `$polar-release`. CI 조사에는 `$gh-fix-ci`, 노트 정리에는 `$changelog-automation`을 활용합니다. 설치되지 않은 환경에서도 이 문서와 저장소 테스트가 기준입니다. 외부 스킬의 예시 명령을 검토 없이 실행하지 않습니다. 사용자 지시와 기존 작업 권한이 우선합니다.

외부 소스는 `docs/agent-skills.md`에 고정합니다. 업데이트할 때 변경 내용을 검토하고 두 프로젝트의 공통 정책을 함께 확인합니다.
